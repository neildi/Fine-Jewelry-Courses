# Building the Weekly Dashboard

## Why This Module Matters

Modules 1 through 5 built the full KPI vocabulary this course is anchored on: conversion, traffic, ATV, UPT, sell-through, turn, GMROI, shrinkage, and retention. A store leader who tracks all of these numbers in eight different places — a POS report here, a spreadsheet there, a mental tally somewhere else — isn't actually using them, because no single view ever shows the whole picture at once. This module builds that single view: a genuinely usable weekly dashboard, following a specific four-row structure that answers the questions a manager actually needs answered, in the order that makes sense to answer them.

## The Core Design Principle: Fewer Numbers, Not More

Across multiple independent dashboard-design sources, one principle repeats with remarkable consistency: limit a dashboard to five to eight headline KPIs, not the fifteen or twenty a POS system is capable of displaying. This isn't a limitation of the software — it's a recognition of how people actually process a dashboard: most people give an overview only a few seconds before deciding what to look at next, and a dashboard crowded with secondary metrics makes the genuinely important numbers harder to spot, not easier. Every additional metric on a weekly dashboard should earn its place by directly changing a decision; a number that's interesting but doesn't change what a manager does next belongs in a deeper diagnostic view, not the weekly headline dashboard.

## A Four-Row Structure That Answers the Right Question at Each Level

A well-documented retail-dashboard structure organizes a weekly view into four rows, each answering a specific, sequential question. Row one answers "was the period good?" using net sales versus plan, transaction count, gross profit margin, GMROI, and sales per square foot — the outcome-level numbers a manager checks first, and if the answer is a clear yes, no further discussion is needed at this level. Row two answers "is it demand or basket?" using foot traffic, conversion rate, average transaction value, and units per transaction — the driver-level numbers that explain why row one looks the way it does. Row three answers "is it inventory?" using sell-through by category, inventory turnover, and out-of-stock rate on top sellers. And a fourth layer, when needed, drills into root-cause diagnostics — specific categories, specific associates, specific SKUs — rather than cluttering the weekly summary view itself.

## Outcomes, Drivers, and Diagnostics: A Framework for Deciding What Goes Where

A related, genuinely useful framework treats every dashboard metric as one of three types: an outcome metric (the few numbers senior leadership reviews every week, like sales versus plan), a driver metric (a number that explains movement in an outcome metric, like conversion rate explaining a sales miss), or a diagnostic metric (used only when deeper investigation is required, and not discussed in every routine review). Applying this framework to this course's own KPI vocabulary: sales versus plan and shrinkage rate are outcome metrics; conversion, ATV, UPT, sell-through, and turn are driver metrics; and category-level or associate-level breakdowns are diagnostic metrics that surface only when a driver metric signals a problem worth investigating further.

## Show Comparison, Not Just the Number Itself

A specific, repeated recommendation across dashboard-design sources: never display a raw number without a comparison point next to it — versus plan, versus the same period last year, versus the trailing four-to-thirteen-week trend. A conversion rate of 11 percent means almost nothing on its own; the same 11 percent next to last month's 15 percent, or next to the same week last year's 10 percent, immediately tells a manager whether to worry or not. This directly echoes the trend-based benchmarking principle this course established in Module 2 for conversion rate specifically, and this module extends that same principle to every number on the dashboard, not just conversion.

## Building It Without It Collapsing by Month Three

A specific, practical warning worth taking seriously: dashboards built from manually retyped numbers reliably break down within a few months, once the manual re-entry becomes tedious enough that someone starts skipping weeks. The fix is structural rather than motivational: export raw data directly from the POS or ERP system rather than retyping it, keep raw data tabs separate from the tabs that calculate KPIs from that raw data (so a format change in one export breaks only one sheet, not the entire dashboard), and build each KPI formula once, referencing the raw tabs, rather than rebuilding it by hand every week. A summary tab that requires zero typing — only refreshing a data connection — is the specific design goal that keeps a dashboard alive past its first few months.

## The Weekly Meeting This Dashboard Actually Supports

A dashboard's value is fully realized only in a specific, recurring meeting built around it: a fixed weekly slot, roughly 30 minutes, on the same day each week, reviewing net sales versus plan, gross profit margin, conversion rate, average transaction value, units per transaction, and sales per labor hour, and ending with concrete outputs — next week's schedule, a promotional focus, and one specific coaching target per associate. This mirrors and extends the five-number weekly review and fixed-slot discipline this course already established in C11's Module 10 (The Manager's Own Weekly Scorecard), giving that scorecard concept a fully built-out, structured dashboard to actually run from.

## Putting the Vocabulary to Work

The practical build sequence for a store leader without existing dashboard infrastructure: start with row one (the outcome metrics: sales vs. plan, transaction count, margin, GMROI, sales per square foot), add row two once row one is running reliably (the driver metrics: traffic, conversion, ATV, UPT), and add row three last (the inventory metrics: sell-through, turn, out-of-stock rate on top sellers). Building all three rows simultaneously from scratch is a common way these projects stall; building one row at a time, getting it genuinely reliable, and then adding the next, produces a dashboard that survives past its first month.

## Practice Exercise

Sketch your own store's four-row dashboard on a single page, listing which specific KPI from this course's Modules 1 through 5 belongs in each row, and next to each metric, note what comparison point (plan, prior year, trailing weeks) you'll display alongside it. Then identify one row you could build this week using only data you can export directly from your existing POS system, without any manual retyping, and commit to running that single row for the next four weeks before adding the next.

## Key Takeaways

- A usable weekly dashboard limits itself to roughly five to eight headline KPIs, since a dashboard crowded with secondary metrics makes the genuinely important numbers harder to spot, not easier.
- A well-documented four-row structure organizes a weekly dashboard by question: row one ("was the period good?") uses outcome metrics like sales vs. plan and GMROI; row two ("is it demand or basket?") uses driver metrics like conversion, ATV, and UPT; row three ("is it inventory?") uses sell-through, turn, and out-of-stock rate.
- Every dashboard metric can be classified as an outcome, driver, or diagnostic metric, and diagnostic-level detail belongs in a drill-down view rather than cluttering the weekly headline dashboard.
- No number should ever appear without a comparison point (versus plan, versus last year, versus trailing weeks) next to it, extending this course's Module 2 trend-based benchmarking principle to the entire dashboard.
- Dashboards built from manually retyped numbers reliably collapse within a few months; exporting raw data directly and keeping raw-data tabs separate from calculation tabs is the structural fix that keeps a dashboard alive.
