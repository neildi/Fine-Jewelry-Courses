# C11-M08 Huddle Card: Writing SOPs Your Team Will Actually Use

## 5-Minute Pre-Shift Discussion

**The one idea to remember:** If a procedure keeps getting ignored, the document is probably the problem — not the team's discipline.

## The Five Ways SOPs Die
1. Written by someone who's never actually done the task
2. Too long — nobody reads past page two
3. Buried — if it takes real effort to find, it won't get used
4. Stale — describes the OLD way, not how it's actually done now
5. No owner — nobody's assigned, nobody checks, it becomes optional

## "Ignored" Usually Means "Poorly Designed," Not "Non-Compliant"
Before retraining anyone, ask: is the process actually clear at the moment someone needs to use it? Is the info scattered across three different places? Does it add work without helping?

## The Seven-Element Structure
**Task → Owner → Timing → Steps → Standard → Exception → Proof**
(Module 2's opening sequence and Module 4's high-value protocol already do this — now name it explicitly when you write.)

## Write What Actually Works, Not What Sounds Right
Watch your BEST associate do the task. Document THAT. Then test it on someone newer — they'll find the gaps an expert won't notice.

## Keep It Findable, Keep It Current
Post it where the task actually happens. Update it the moment the real process changes — not on some arbitrary schedule.

## Today's Discussion Prompt
Pick one SOP we already have. Does it pass all five failure-mode tests, or is it quietly broken in one of these ways?
